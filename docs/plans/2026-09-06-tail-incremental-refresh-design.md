# 楼中楼尾部增量更新设计

状态：用户已批准；实现与验收已完成。分支：`opt/comment-collection-performance`。

## 目标与范围

用户已确认将经过样本验证的尾部增量作为更新快速路径。减少已有大楼新增回复时的重复分页，同时保留完整获取、异常回退、来源限制及可信覆盖标记。此文是已批准设计，实现及验收见关联计划。

本阶段不改变首次采集、主评论完整游标扫描、每页20条、共享限速、小时缓存、正常读取不触发刷新等规则。不同时实施空楼跳过、并发、检查点整体重构、直接入库、讨论浏览或AI分析。

## 可行性边界

现有样本支持直接按页码读取、回复按时间从旧到新排列，以及尾部追加时重叠回读补齐ID集合。离线回放不能替代真实新增、删除、重排的长期验证；有限重叠检查无法发现所有中间修改和等量替换。因此快速路径只提供部分重新观察的结果，不能承诺整个楼在同一时刻被完整核验。

## 启用条件

仅对同时满足以下条件的楼尝试尾部增量：

- 当前任务有效模式为 incremental；显式 full 或既定完整核对周期到期时仍完整获取。
- 本轮主评论扫描实际观察到该楼，根评论规范化正文及身份/归属未出现矛盾。
- 有可信、未失效的分页基线：来源顺序、回复数、页大小和尾部边界来自完整获取，或由已校验的尾部追加链推进。
- 本轮主列表报告的回复数严格增加；旧回复至少占4页。小楼继续完整获取，避免复杂流程只省极少请求。
- 页大小仍为20，基线中没有不可用、身份冲突、无法归类或沿用的额外回复导致的数量矛盾。

旧数据没有分页顺序证据时，不从评论ID排序或发布时间排序伪造来源顺序；对本轮需更新的该楼完整获取一次以建立基线，不因此重抓整个视频。回复数未变的楼沿用既有缓存策略及周期核对；不能宣称其正文或回复完全没有变化。

## 分页与合并算法

设旧来源回复数为 N0，每页 P=20，旧末页 L0=ceil(N0/P)。起始页 S=max(1,L0-1)，回读旧末页和其前一页，再继续读取本轮尾部。

1. 冻结旧基线及视频缓存版本，记录此次选择的策略与原因。
2. 从 S 页请求，要求返回页码、大小、楼归属正确；第一页报告的新总数 N1 必须与本轮主列表报告一致且 N1>N0。
3. 此次返回序列的旧重叠段，必须与基线保存的有序ID序列完全一致，不能只比较数量或无序集合。
4. 继续读取到 ceil(N1/P)，每页总数必须保持 N1，检查异常空页、重复ID、跨楼记录和时间倒序。时间相同允许，以来源ID顺序作为锚点，不假定数值ID全局递增。
5. 旧重叠段之后的ID必须是基线中不存在的新回复；新增去重数量恰好等于 N1-N0，最后一页实际条数应符合总数。
6. 所有检查通过后，才按评论ID合并：重叠段更新实际观察到的规范化记录，新增ID加入，未读取的旧记录保留原观察时间。
7. 更新尾部边界和最新追加观察计数，保留上次全楼完整核对时间；最终发布仍经既有原子入库与任务所有权校验。

例：旧397条、新398条，S=19，仅需第19、20页；旧400条、新401条，需要第19、20、21页。节省的是该楼分页请求，并非整个视频同比提速。

## 比较哪些字段

锚点主要核对ID及来源顺序，同时验证根楼、作者UID、父评论关系等身份约束。规范化正文、图片、表情和实际存储字段沿用既有数据契约；重叠段的正文或点赞等更新应保存。

不对整个原始响应做等值判断。未进入当前存储契约的附加展示字段变化，不应单独导致整楼重抓。新增语义字段必须按契约纳入比较，不能为提速忽略应保存的变化。

## 回退与异常

| 情况 | 行为 |
| --- | --- |
| 回复数减少、基线缺失、根正文变化、不可用状态或页大小变化 | 直接走既有整楼获取 |
| 重叠ID/顺序错位、计数波动、重复页、新增数量不符 | 本任务该楼禁用尾部路径，回退整楼获取一次 |
| 已有评论改动但身份及分页锚点一致 | 保存本轮读取到的更新；未读区域仍标记沿用 |
| 来源拒绝、鉴权失败、限流 | 按既有规则暂停，不以回退路径绕过闸门 |
| 网络中断、取消、租约丢失、预算不足 | 保存恢复信息并遵守现有状态机，不重置预算 |
| 回退完整获取仍不完整 | 保留partial及已有可读数据，不无限反复切换策略 |

## 检查点与恢复

尾部尝试按楼、尝试编号和页码保存候选页，候选数据与正式已确认工作集分开；请求预算与候选页提交仍需持久化。全部尾部校验通过后原子合并候选数据与证据，失败不把尚未通过核对的候选内容标为已确认。

回退使用独立分页键，不能因尝试过尾页而跳过完整获取的同页。中断后重入尾部尝试须从重叠边界重新验证，不盲目沿用旧页码；累计请求预算保留。已经提交完成的楼不重复处理，其他已完成楼的成果不回滚。

## 证据结构与兼容

在现有工作集与数据库 refresh_context 内增加可选、带版本的尾部证据，不新增公开导出枚举。建议内部 tail_evidence v1 包含：

- source_count、page_size、root_signature及验证过的根身份；
- anchor_start_page、按来源顺序保存的尾部ID序列，最多两页；
- latest_tail_checked_at、last_full_checked_at及证据有效状态。

尝试状态另存策略、基线计数、目标计数、候选页、尝试编号和回退原因。最新追加计数与历史 checked_count/last_complete_at 分开，不能用尾部成功冒充新的全楼核验。下一轮策略选择可使用经过验证的最新计数，但其完整核对周期始终以 last_full_checked_at 为准。

现有无尾部证据的记录继续可读，只是不具备快速路径资格。存储交接、基线恢复、CLI恢复需共同校验新字段；无法识别或不合法的可选证据不用于加速。证据写入前后保持原子发布版本防护。是否需要调整持久结构，由实施计划明确；不混跑不识别新恢复状态的旧worker。

## 完整性与对外行为

- 尾部尝试完成不等于全楼重新核验；内部需要独立完成标记，避免采集循环再次处理，但不能设置 checked_now 或推进完整核对时间。
- 快速路径成功仍对外使用既有 partial、沿用数据和上下文覆盖提示，不新增未经版本化的协议值。新增及重读ID进入本轮观察集合，其余记录保持沿用。
- 继续兼容导出协议v2与v1读取；UID、评论ID、根楼关系和用户归类不变。
- 整体任务可按既有规则完成为partial；不得因为新增数相符而隐藏来源缺口。
- 仍由显式刷新触发；周期到期只影响下次请求策略，不添加自动采集。

## 验收要求

以完整获取作为同一固定数据源的对照，验证尾部方案的ID集合、正文及回复归属；不得用不断变化的两次真实读取假装严格快照对比。

必须覆盖：末页未满追加、跨页追加、整页边界、多次连续尾部刷新、重叠错位、删除、数量变化、重复页、异常空页、页大小变化、旧基线缺失、周期到期、原始附加字段波动、取消及断点恢复、回退预算累计和原子发布冲突。

明确加入中间等量替换与未读正文修改的边界样例：尾部可能无法识别，结果必须保留partial，且不能延长完整核对周期。

性能验收采用固定样本的来源请求数和分阶段耗时：397→398纯追加场景由20页降为2页，400→401读取3页；回退场景允许增加少量探测成本，但有明确预算且不循环。真实视频做有限对照验证，临时数据仅存忽略目录。
