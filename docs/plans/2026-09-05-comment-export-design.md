# 视频评论文件导出：设计

## 数据契约

已审阅的数据格式固定为 [评论导出协议 2.0.0](../references/comment-export-protocol-v2.md)。字段、目录、完整性、发布与消费规则以该标准为唯一依据，本文件不再重复维护副本。

## 当前范围与决定

从同一冻结数据批次生成按楼和按 UID 的文件副本，以便独立脚本处理。采用 JSON 元数据和 JSONL 评论；README 暂为空；导出不调用大模型。

脚本必须接受调用方传入的视频链接，不得固定视频身份。本次仅用于调试的目标为 `https://www.bilibili.com/bangumi/play/ep4292435/`。由独立 Python 脚本解析并采集，服务器执行不依赖 Agent 或桌面浏览器。旧视频数据不能混入新目标。

发布采用按视频的 current.json 原子切换；消费者遇到旧批次清理时整批重读。用户元数据同时携带分页覆盖与上下文缺口信息。只保留当前批次及最近一次工作数据，不提供历史归档。

## 阶段边界

协议已定版；CLI、Schema 和语义校验器已实现，新视频全量验证仍在进行。按实施计划完成真实覆盖验收。网页样式、模型分析和服务器上线仍属于各自阶段，不在本设计中一并实施。

## 英文目录升级

用户确认目录需适合服务器存储，改为threads/<序号>和users/uid_<UID>；昵称仅保留JSON字段，未知作者目录为users/unknown。此为目录契约的破坏性变更，发布2.0.0，保留1.0.0读取，不原地重命名旧批次。

实现步骤：补充版本2路径及多评论楼测试；按版本选择Schema和目录规则；CLI及数据库导出统一生成2.0.0；核验数据库往返和索引扩展保留；使用已采完整工作集重新导出并逐条比对，提供唯一明确的新交接入口。无需重新请求Bilibili。

单记录楼需结合reply_count和分页覆盖解释，不能只凭文件长度判断丢失；旧的中间导出批次不会自动补写。当前数据通过D:/Data/exports下的视频current.json访问，旧样例不作为当前交付入口。源端不可得的回复继续保留partial标记。
