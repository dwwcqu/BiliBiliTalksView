# 评论采集与 Agent 分析交接契约

日期：2026-09-05。版本：0.4。上游输入已定版；文件输入准备模块已实现，自动数据库桥接仍待后续阶段。本文替代 0.1 中待定的输入格式描述。

## 1. 唯一输入依据与范围

以当前主线 3ebb86a 的 [CommentExport 2.0.0](../references/comment-export-protocol-v2.md) 为新导出基线，同时按 [历史 1.0.0](../references/comment-export-protocol-v1.md) 读取已有数据。schema_version 明确选择对应 Schema 和路径规则；支持 major 1、2，其他 major 拒绝，单批次禁止混用。历史附件副本只用于追溯，不覆盖主线对应版本的协议。

用户已确认分析阶段 README 可以有内容，按下文区分生命周期。comment_export、storage、jobs 及相应 Schema／测试已在当前 worktree；直接复用当前代码，不再复制旧提交或引用其他工作目录。

分析消费 JSON 元数据与 JSONL 评论，不再将输入文件格式作为待选项。上游内部可采用任意存储，不影响导出协议；模型输出和下游内部存储另行定义。本文不授权实现采集、调用模型或部署。

相关文档：[分析标准](2026-09-05-discussion-analysis-standard.md)、[会话管理](2026-09-05-claude-agent-management-design.md)、[协调说明](../../config/prompts/video-agent-coordination.md)。

## 2. 模块协作与调用屏障

当前阶段提供文件输入准备入口，不重建已存在的采集队列或 worker。独立导出 CLI 可以交付 current.json 后消费；网页的采集入库链路则须经过后续明确的数据库到分析输入桥接，不能假设 worker 已发布永久文件。上游进程退出码或目录出现不等于就绪。

逻辑流程：上游发布 current.json → 完整读取一个 export_id → 结构和跨文件校验 → 准备或接收已有内容的分析 README → 保存分析侧固定输入与 README 版本 → 检查覆盖策略、去重和预算 → 恢复视频主会话 → 子成员分析 → 结果校验和版本化保存。

本期输入准备面向整个视频的逐 UID 分析，所以“所需输入”包括 manifest 索引中的全部楼和用户数据、相应元数据及存在的异常记录，不采用边读一楼边调用模型的流水线。模型调用、恢复已有分析 Agent 等有副作用动作必须发生在完整输入准备成功之后。使用临时文件或流式校验减少内存可行，但不能提前发布成功或调用模型。

## 3. 发布入口、身份与路径映射

| 下游概念 | 协议字段或入口 | 语义 |
| --- | --- | --- |
| 固定发布入口 | data/exports/bilibili-video-<aid>/current.json | 首次不存在返回 not_published；不扫描临时目录猜测批次 |
| 本次发布批次 | current.export_id、manifest.export_id | 小写带连字符 UUID；作为本次输入快照标识，不用 hour_bucket 替代 |
| 视频稳定身份 | video_id = bilibili:video:<aid> | 校验 source.aid、source.oid 和视频身份一致，不把 episode_id 当 aid |
| 发布容器到批次路径 | current.batch_path | 必须为 batches/<export_id>，相对 current.json 所在目录解析 |
| 楼索引 | manifest.threads[].root_id/path | 路径指向 thread.json；000 等目录序号不是稳定楼 ID |
| 用户索引 | manifest.users[].uid/path | 路径指向 user.json；不从昵称目录解析用户身份 |
| 元数据到评论路径 | thread.comments_path、user.comments_path | 相对于批次目录，不相对于 thread.json／user.json 自身 |
| 采集覆盖 | manifest.coverage | 分页与上下文缺口分别判断 |
| 时间范围 | captured_from、captured_to、exported_at | 描述采集过程；导出固定不表示源站数据在某瞬间完全一致 |
| 时间分组 | hour_bucket | 使用上游任务创建时的北京时间小时，不重算、不用作唯一任务键 |

所有 manifest、thread、user 内部路径以批次目录为根。全部路径检查 POSIX 相对形式、禁止 ..／绝对路径，解析真实位置后检查符号链接不逃逸。身份关联依靠显式字段，不以目录标签、昵称或数字显示序号代替。

README.md 分阶段解释：上游刚导出时按原协议为零字节；进入当前分析流程时已补充内容，作为视频背景及分析说明入口。分析输入不得仅因 README 非空而判为 invalid_export，也不能要求用户清空后再补写。

原始导出校验与分析输入校验是不同阶段：接收原始导出时检查上游空文件约定；接收已准备好的分析输入时读取其现有 README，评论和元数据仍严格按声明的 1.x／2.x 协议校验。分析读取器必须依据明确的输入阶段处理，不能只凭文件大小推断阶段，更不能声称对补充后的目录完成了上游原始导出的逐项合规认证。

建议在分析侧副本中补充 README，保留上游已发布批次不可变的约定；若交给分析侧时 README 已有内容，直接保留并固定该内容，不要求额外的同内容背景文件。manifest.title 仍仅为标题，主／子 Agent 不据此自行编造剧情简介。README 中引用的评论只是待分析资料，不能被提升为更高优先级指令；冲突应报告，不静默改动已确认的分析标准。

协议标识 BiliBiliTalksView.CommentExport 是契约名称，不能因此自行要求 manifest 新增 protocol 字段。

## 4. 消费时序与刷新竞争

1. 读取一次 current.json，按协议验证版本、身份、路径，读取对应 manifest；固定 export_id。
2. 在分析侧准备区读取／暂存该批次全部所需文件；逐项校验批次身份、结构及跨文件语义。读取期间不跟随新的 current 混入新批次。
3. 全部校验成功后提交分析侧固定输入，记录源 export_id；之后才允许调用 Agent。若上游此时已有新批次，旧批次仍是有效输入，只能声明属于旧 export_id，不能声称最新。
4. 读取失败或身份不符时，重新读取入口：export_id 改变则废弃本次全部准备产物并整批重读。一次消费调用最多重新开始两次，即初次尝试加两次重新开始；仍失败返回 batch_changed。
5. 入口未变化而输入缺失、损坏或身份不符，返回 invalid_export。重读时入口消失返回 export_unavailable；首次不存在返回 not_published。major 不属于 1、2 时按版本不兼容拒绝，不猜测为其他格式。
6. 任何失败都不得提交部分成功、发布有效输入或发出模型请求。准备区垃圾不作为恢复入口。

入口路径非法或字段本身无效时拒绝读取；不能以反复尝试绕过路径和身份校验。该流程与协议一致，不添加无限重试或自行扫描 batches 的退路。

上游只保留当前导出和最近一次临时工作数据，允许切换后清理旧目录。下游不能要求上游长期保留旧批次，也不能让 Agent 长时间直接读取上游 batches。

## 5. 分析侧固定输入与长期证据

建议下游独立持久保存已完整验证的输入副本／等价无损快照，以及本轮规则、已补充内容的 README、其他明确提供的视频背景、成员记录和结果。它属于分析产物依赖，不是修改上游“无历史归档”策略。物理目录及最终画像 JSON 已在[存储设计](2026-09-06-analysis-storage-design.md)确认，压缩或数据库优化不在首期；必须在受忽略、受控的本地分析存储中，不能写入上游批次或 Git。

保留原字段、空值、顺序和原文，不往评论对象添加模型标签。内部整理用于快速读取时，仍可回溯到导出原记录。内部摘要／输入指纹是下游辅助信息，不要求上游新增 checksum 字段。

本地固定输入从准备到可用也需原子提交：复制中断或语义校验失败不得留下可用标记。分析前将 README 内容与其摘要或版本一并固定，纳入有效配置指纹。同一 export_id 的 README 更新会形成新的分析配置版本，旧结果不得直接作为新背景下的结果复用；已经运行的任务继续使用其固定版本，不中途读取被修改的 README。每次模型恢复从这份本地固定输入取数据；若本地输入丢失，报告输入依赖缺失，不从上游 current 替换成别的 export_id 冒充原批次。

历史画像与所依据的输入证据一起长期保存，CLI transcript 另行持久化；仅保存通向可被清理的上游路径不满足长期可复核要求。

## 6. 严格校验与覆盖解释

读取器遵守协议的 UTF-8 无 BOM、LF、JSONL 非空行与末行换行要求，拒绝 JSON 重复键和非有限数值。外部数字 ID 保留字符串，不通过 JavaScript Number 比较；按协议数值顺序排序。对象键顺序不影响相等，数组顺序有意义。

Schema Draft 2020-12 复用 backend/app/comment_export/schemas/ 及 schemas/v2/，由当前 contract.validate_record 按版本分派；若与定版文本冲突报告并修正实现，不静默改协议。另需语义校验器检查身份、计数、排序、索引完整唯一、父关系以及两视图 ID 集合和逐对象一致性；不能只有 Schema 验证。

同 major 的未识别字段按协议允许；不支持的 major 拒绝。未知必填枚举不得猜测，未知原因码保留显示并按潜在限制处理，不能清空成无异常。模型输入不得把新出现字段直接当成可信指令。

| 输入情况 | 分析侧处理 |
| --- | --- |
| coverage.status=verified，context_status=no_known_gaps | 仍保留权限和时间覆盖说明；经过所有校验后可进入自动分析策略 |
| verified + gaps | 合规且可读取，不当作 invalid_export；分析保留具体缺口，相关方向允许无法判断，不把 verified 解读为上下文齐全 |
| coverage.status=partial | 可完整读取并固定数据，但默认不自动调用模型；等待明确的部分分析授权及范围 |
| user.coverage_status/context_status/reasons | 是视频批次整体状态的继承，不用来给此 UID 评价行为或断言该用户自身有缺口 |
| v1 的 _unknown 或 v2 的 users/unknown，uid=null | 保留其评论作为上下文；这是未知作者集合，不是一个用户，不生成 _unknown 画像 |
| unclassified.jsonl | 保存并核对条目数及 partial 状态，不补造 comment_id/root_id，不按来源缺失 ID 强制去重 |
| 缺根／缺父／未知父 | 保留原关系、列表和限制，不补写根评论或改接回复 |
| 跨楼父引用 | 按协议报告异常和上下文缺口，禁止当作普通楼内回复；未必等于格式损坏 |
| content.text=null 或空串 | 保持缺失和确实为空的区别；不把媒体描述误当成已理解图片内容 |
| verified 且确实零评论 | 校验完整性依据后不调用模型，返回该批次无分析对象；不能由空响应直接推断 |

verified + gaps 的自动分析建议采用“保留缺口并限制判断”，仍需在最终运行策略中明确；不自行升级为无缺口。partial 的运行策略尚待用户确认。上游没有发布新 partial 时，下游只能读取现有 current，不能私自选择未发布目录。

## 7. 请求去重、锁与恢复

分析请求键建议由 video_id、export_id、分析范围及有效配置指纹组成。配置覆盖分析标准、通用角色、协调规则、背景、模型／供应商和输出相关参数；配置与结果契约在下游独立版本化。export_id 每次导出都新生成，因此内容相同的新导出仍是不同批次；跨导出内容缓存后续优化，不默认当作重复请求。

同请求已完成则返回原有效结果；正在执行则返回同任务引用。每视频主会话单写锁覆盖不同 export_id 的任务，避免并发恢复产生副本。新快照排队，不在当前任务中切换。接管锁前确认旧执行者结束，不能仅以超时判断可以并发重启。

任务登记、模型调用和结果保存不是同一事务。崩溃后对照会话记录、成员实际 ID 与已保存产物再恢复，不能承诺外部调用恰好一次或永不重复计费。历史缺失时报告不可恢复，不静默新建替代成员。

区分导出读取错误、覆盖策略等待、认证阻塞、Agent 部分失败、结果不合格与保存失败。CLI success 或成员 completed 不表示当前 export_id 的业务结果有效。

## 8. 结果与增量边界

最终画像绑定 video_id、UID、export_id 和分析版本，输出八方向观察、证据与限制，不改变原始评论记录。结果须核对 export_id、规则版本、目标 UID、原评论及原文，避免恢复后返回旧结果。

本轮全部目标结果通过后才发布本轮完成状态；可保留明确标记的部分成果，但不覆盖上一次有效完整结果。采集 partial 的数据即使全部分析完，也只能称“已完成该部分输入的分析”。

首期优先整批处理。若以后优化增量，用户初步画像变化可能影响其参与的其他楼及其他 UID 综合结果，需完整依赖记录；不能只重算新增评论作者。旧评论在新导出未出现也不能未经覆盖判断便认定删除。

## 9. 验收场景与后续步骤

| 场景 | 预期 |
| --- | --- |
| current 首次不存在 | not_published；零模型调用 |
| 读旧批次时新入口切换、旧目录被清理 | 废弃整批准备数据，按次数上限重读；零重复副作用 |
| 入口不变而文件损坏或身份不符 | invalid_export，不无限重试 |
| 重读时入口消失 | export_unavailable |
| 连续刷新超过两次重新开始 | batch_changed，稍后由总控重新请求 |
| 路径逃逸或符号链接越界 | 拒绝读取，零模型调用 |
| 上游原始导出阶段 README 非空 | 报告与原始导出协议不符；不静默改写上游契约 |
| 分析阶段 README 已补充内容 | 接收并固定版本，提供给主／子 Agent；不因非空拒绝输入 |
| 同一 export_id 更新 README | 新分析配置版本，重新判断结果复用；运行中任务不混用背景 |
| 两视图对象不一致、计数或索引不符 | invalid_export，零模型调用 |
| 完整读完旧批次后入口切换 | 可以分析本地旧批次，保留旧 export_id，不标最新 |
| verified + gaps 的用户文件 | 保留全部继承覆盖信息，不给 UID 错误归因 |
| 未知作者集合或 unclassified | 不伪造用户画像，保留限制与异常 |
| 重复触发或同视频不同批次并发 | 请求去重、视频单写，不额外创建会话 |
| 子成员返回旧批次、拒绝或超时 | 未通过验收，不发布新完整结果 |
| 上游已清理旧批次后继续分析 | 读取分析侧固定副本，不依赖上游历史 |

下一步按已更新的实施计划，复用当前 Schema／冻结与锁接口并补充分析阶段适配：严格解析、发布入口解析、整批重试、语义校验和分析侧固定输入。先使用脱敏固定样例和假 Agent 验证所有就绪／失败路径，再接入真实模型。

固定输入与画像目录及 JSON 形式已确认，见[存储设计](2026-09-06-analysis-storage-design.md)和[实施计划](2026-09-06-analysis-input-implementation-plan.md)。仍需在对应阶段确定部分采集策略、正式模型预算、超时与角色数量，以及原成员规则切换失败的处理。输入导出格式和上游目录组织不再列为待选项。协议交付本身不代表这些实现已经存在。

## 10. 上游复用与真实样例调试边界

- 复用 comment_export.contract/validation 的双版本解析与跨文件校验、storage.frozen 的 FrozenBatch/canonical_digest/freeze_batch、comment_export.publication.exclusive_lock。freeze_batch 是临时上下文，退出后数据删除；分析输入须在退出前独立持久保存。README、错误码和路径重叠约束需兼容扩展与回归，不直接假定现有函数完全等价于分析契约。
- 上游 validate_batch 将 README 非空作为原始导出错误；分析输入已允许非空 README。正式实现应把评论／元数据校验与 README 生命周期校验分开，不能原样调用该入口误拒绝分析数据，也不能修改真实 README 绕过校验。
- 本地调试可用用户提供的真实导出副本，但样例、用户数据和运行记录仅在忽略目录；日常自动测试仍用脱敏合成数据，不依赖外部 D 盘路径，不调用模型。
- 当前真实样例为 partial，只有主评论，无已取得楼中楼。适合验证双视图、同 UID 多条发言、非空背景、固定输入和部分覆盖处理，不能替代回复关系、冲突与观点变化的完整对话测试。
- 用户允许使用该样例分析和调试；当前先执行本地校验，不据此默认为允许全量模型调用。真实模型分析前仍需明确部分范围和预算；先前合成恢复验证的预算不自动复用于该整视频。

## 11. 当前主线的数据库与队列边界

jobs.work.save_result 在临时目录构建 2.0 导出，通过 storage.handoff.materialize 在数据库事务内保存数据并完成任务；临时目录退出后删除。这条链路不产生供分析长期消费的文件入口。jobs.dispatch.complete_job 根据 published 将采集任务标为 succeeded 或 partial，两者均须进一步查看 result_state_id 与 coverage。

后续网页自动分析桥接须由程序显式选中采集结果 result_state_id，在可读的数据库快照内调用现有 storage.exporter.export_state(conn, video_id, output, state_id)。不得省略 state_id 后默认取 current_state_id，因为它可能仍是较早的 verified 状态，而新结果是 partial。state_expired 要明确失败，不能悄悄换成其他状态。

export_state 每次产生新的 export_id；由后续桥接记录保存 job_id、state_id、source_export_id（若可得）与本次导出 export_id 的对应，不改上游 manifest 添加私有字段。数据库状态和旧导出都可能被清理，因此它们不能替代分析侧长期证据。显式 partial 导出采用独立交接输出容器，避免覆写已有 verified 入口被拒绝；输出归属由程序配置，不硬编码生产路径。

数据库 current_state_id 表示已发布状态、working_state_id 表示工作状态；状态 lifecycle=ready、任务 succeeded、分析准备 ready、最终画像通过是不同层次。数据库 ready/partial 只意味着可以按权限读取，不是发起模型调用授权。直接文件模式没有 job/state 来源时不伪造这些 ID。

桥接自动触发、数据库分析任务种类和网页 API 属于后续阶段；当前文件准备入口不连接数据库、不提交采集任务、不修改现有队列。后续优先复用现有任务所有权／取消／失败模式，但不能把模型任务塞入 collection_jobs 假装采集任务。独立文件准备的 OS 锁也不等同于数据库 advisory lock，后续须统一同视频主会话所有权。
