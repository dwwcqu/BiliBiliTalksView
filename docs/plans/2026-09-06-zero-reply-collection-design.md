# 零回复楼请求优化设计

状态：用户已确认，实现与验收已完成。分支：`opt/zero-reply-collection`。

## 目标与已确认边界

在楼主评论始终完整保存的前提下，减少零回复楼不必要的详情请求，主要改善网页首次采集和普通更新。依据[有限验证设计](2026-09-06-zero-reply-validation-design.md)中的正反例约束实施；样本一致不等于所有来源状态都一致。

不改变主评论完整游标扫描、每页20条、共享限速、小时缓存、用户/回复关系及已有尾部增量。并发、直接入库和检查点整体重构不在范围内。

## 方案选择

| 方案 | 收益与取舍 |
| --- | --- |
| 所有零回复楼仍访问详情 | 维持现状，首次采集不能显著提速 |
| 所有模式都相信主列表零计数 | 请求少，但失去显式完整核验和周期兜底，不采用 |
| 普通auto按条件省略，full和到期核对访问详情 | 推荐；以明确的部分观察语义换取请求减少，保留严格核验路径 |

已确认的核心取舍：普通首次auto允许保存“仅主列表报告零”的partial结果，不将其表述为详情已核验。来源在主列表读取后新增回复可能延迟到后续刷新或完整核对才发现。

## 策略入口

将零回复策略与现有full/incremental扫描范围分开，内部冻结为 `observe` 或 `verify`，不增加公开模式枚举。

| 场景 | 零回复策略 |
| --- | --- |
| 网页首次提交、无缓存的refresh --mode auto | observe：完成主列表扫描，符合条件的零回复楼可省略详情 |
| 有可信基线、未到期的普通auto更新 | observe；非零楼继续使用已有复用/尾部/完整策略 |
| 实际新建并按full冻结的CLI/HTTP任务 | verify：零回复楼也访问详情 |
| auto触发到期完整核对 | verify，不通过优化推迟到期任务 |
| 原独立collect命令及直接调用的默认full | 保持verify；首次想使用优化可用无基线的refresh --mode auto |
| 已有基线但缺少可信调度证据，或旧恢复任务缺少冻结策略 | 保守verify，保持兼容 |

首次auto的扫描范围仍可为full，表示检查全部主楼及需要请求的回复，并不意味着每个零回复楼都访问了详情。实际新建并按full冻结的任务保留逐楼详情核验的含义。现有活动任务和同小时请求仍按原规则去重；full请求若复用已有auto任务，不改写原任务策略，也不能表述为已开始full核验。需要full核验时，须等待原任务结束并满足原刷新资格后新建；不绕过小时限制。

## 候选规则：全部满足才能省略

1. 正常成功的本轮主列表响应，主评论ID、视频归属及根身份合法；完成既有规范化和保存。
2. `rcount`字段存在且类型严格为整数0；不将缺失、null、布尔、浮点、字符串或负数解释成零。
3. 若响应存在辅助回复计数，必须也是合法整数0；若有预览，只接受空数组、null或不存在。非空或格式异常预览拒绝省略。
4. 本次完整主列表扫描中，同楼所有观察均不矛盾；任何一次非零、非法或预览冲突都使本任务该楼失去资格，不能被后面的零覆盖。
5. 本地没有该楼的已保存回复；该楼相对于本任务冻结基线为本地首次发现，或有完整版本化的本地历史标志，且历史非零/不可用标志均为false。已有旧楼缺少历史字段不等于无历史，拒绝省略；任何反证优先于当前零报告。
6. 当前冻结策略是observe，且本任务不是到期完整核对。

候选身份、计数、预览和冲突信息需在主列表页事务中保存。全部主列表分页结束后再最终选择，不边扫描边作不可撤回的零楼完成决定。置顶重复楼同样合并观察，不能重复计数。本地首次发现以任务准备时冻结的基线判断，不以当前页刚写入的记录判断；该身份及历史标志与首次主评论写入同事务保存，恢复不能重新认定为新楼。

本轮没有再次观察到的旧楼，不能沿用历史零证据执行零省略；走已有缺席楼处理路径。原增量逻辑已决定复用的楼也保留原路径，不重复归因于零优化。其余原本需要请求详情的楼才应用候选规则。未命中规则不是失败，直接沿用已有详情获取逻辑。历史有回复而本次为零时保留旧评论，访问详情核对；不得为减少请求删除已保存内容。

## 调度与完整性分开记录

现有last_full_scan_completed_at与full_scan_incomplete必须继续表达完整范围详情处理证据；存在省略详情的零楼时，不推进完整核对时间，也不假装full_scan_incomplete已消除。

新增独立版本化的可选 `zero_reply_schedule` v1，至少包含：

- `scan_completed_at`：所属轮次主列表到尾、所有已保存楼完成所选处理后的时间，不等于详情全部核验。
- `verification_anchor_at`、`verify_interval_hours`、`verify_due_at`：期限来源与绝对期限，不只保存一个可任意移动的时间戳。
- `scan_policy`、视频ID、本轮任务/导出ID、基线版本（无数据库时用基线摘要）、主列表到尾标记及按楼处理结果的绑定摘要。

首次真正无基线auto在首次准备阶段冻结策略和起始时间；其成功observe结果以该时间加完整核对间隔建立期限，失败或重试不重置起点。有既有完整核对证据时，沿用其期限，不因第一次采用零优化而额外获得24小时。默认间隔仍为24小时，worker保持24小时；CLI使用既有full_interval_hours。新的用户请求缩短间隔可以提前核对，延长间隔不得推迟已经冻结的期限；恢复保持原冻结参数。

真正完成verify整轮后，以原完整范围核对完成时间重新建立期限。来源返回楼不可用时仍保留partial，但沿用现有“已尝试完整范围”的调度含义，不表示所有评论均可得。取消、预算用尽、分页未结束、未处理的楼或未完成的候选页不能生成完成证明。

**新建任务的选择顺序：**

1. 已有活动任务优先按原规则复用，不在复用过程中改变策略。
2. 实际新建的显式full任务使用verify。
3. 真正无基线、没有待恢复检查点的新建auto任务，允许full扫描范围加observe策略；这是明确的首次例外，不被“缺少旧证据”规则覆盖。
4. 有基线时先验证证据；任何有效期限已到期，使用full范围加verify。存在多个可验证的期限依据时取最早期限，普通更新不能选择较晚者绕过复核。
5. 兼容有效旧版完整证据；否则仅在新版scan证明与逐楼结果绑定有效、尚未到期时允许incremental加observe。已有基线但缺少可信完成证据，使用full范围加verify。

**跨期限恢复：**既有observe任务恢复时仍执行原冻结策略，可以完成为partial，但不延长verify_due_at。若完成时已经过期，下一次实际新建auto任务必须verify；本设计不承诺在一个运行中的任务内自动切换策略。没有用户刷新就不自动发起任务，因此24小时是下次请求的策略门槛，不是无人操作时也能保证的数据时效SLA。

完成证明必须绑定本轮视频、基线和已确认数据：每个已保存楼都需有本轮合法零省略、既有规则允许的复用/尾部完成、详情处理完成或有效源端不可用结论；任一未完成楼使本轮证明不能成立。零省略必须对应本轮真实主列表观察集合。沿用历史证明时保留其原所属轮次、期限和摘要，不更新scan_completed_at来假装新轮已完成。不能只看status=partial或一个时间戳就认定可增量。

## 楼级证据与周期状态

使用可选 `zero_reply_evidence` v1保存：video_id、root_id、主列表观察时间、来源计数字段的有效零结论、空预览结论、根身份绑定和证据来源 `main_list`。持久化与本任务主列表实际观察集合相互核对，不保存原始接口响应或新增大段正文。

本任务省略详情的完成标记与历史reply_check_state分开：不调用checked_thread，不写checked_now，不伪造last_reply_checked_at。新楼无历史详情核验时仍保持needs_check；采集循环用独立的本任务处理标记判断无需继续请求。

独立保存 `zero_reply_history` v1：`ever_nonzero_observed`和`ever_source_unavailable`。本阶段两项标志只允许false变true；刷新、详情再次为零、checked_thread、工作集恢复或数据库交接均不得清除。主列表/详情非零计数、非空回复或已保存回复均构成非零反证，楼不可用结论构成不可用反证；普通网络失败不冒充楼不可用。

本地首次发现的楼可以从其首个已保存观察建立这组标志；已有旧楼的缺失/损坏/未知版本历史标志表示unknown，不能填false，也不能用一次新详情零结果抹掉未知历史。已可见的非零反证可以将unknown收紧为禁止省略。旧楼继续使用已有完整获取或原增量复用策略，避免为初始化历史而额外全视频重抓。新字段丢失或无法验证只丧失加速资格，不丢失评论。

之后主列表出现非零、预览、计数冲突或本地回复记录时，零证据失效，进入正常详情获取；旧零证据不能作为尾部增量锚点。完整获取完成后，零观察不再替代该次详情核验结果。

## 对外呈现与协议兼容

只要本次省略了任何零回复楼详情，该楼分页及整体覆盖保持partial，沿用现有replies_incomplete等兼容表达；不能输出“详情已核验为空”。根评论、作者对应与所有已保存回复照常导出。

公开JSON/JSONL v2目录和枚举不变，内部证据及调度字段不直接导出。通过各自state摘要的可选安全字段 `zero_reply_observed_threads` 返回该结果所属轮次实际观察、实际采用零省略处理的不同楼数；不计历史零证据、缺席旧楼、原增量复用或已另行访问详情的楼。旧状态缺失该字段时前端仅隐藏专用提示，不由此推断所有详情已核验。前端只在大于0时增加说明：“其中X个楼仅依据主列表报告零回复，尚未访问详情核验”。不新增讨论浏览页面。

current和最近partial各展示自己所属状态的计数，不能混用最新任务或另一个状态的数字。该计数由入库时已验证的楼级证据计算并原子保存，读取摘要无需加载所有评论正文；禁止直接信任外部输入或缓存中未经校验的统计数字。客户端校验可选字段为非负整数，旧接口响应继续可用。

## 内部协议兼容

保持现有refresh_context外层version=1及公开协议版本；zero_reply_schedule、zero_reply_evidence、zero_reply_history各自是独立版本化的可选扩展，不直接提升外层版本。collector/checkpoint写入、prepare_refresh复制、handoff白名单校验/保存、baseline恢复和API安全摘要须同时贯通，不能依赖当前白名单自动保留新字段。

有效旧版核心证据保持可用。缺失、损坏或未知版本的可选扩展不能让旧基线整体不可读，只禁用依赖它的零加速或新调度证明，并按上述模式优先级降级；核心身份/封装本身损坏仍按原存储错误处理。不得在过滤扩展时删除能够确认的历史反证，unknown不能转换为false。部署时停止旧worker，不混跑会丢弃扩展字段的旧写入进程。

## 事务、恢复与错误

主评论和候选观察同页提交。零楼处理标记、覆盖及调度更新保持可恢复和幂等；中断后重新检查资格，不能因旧完成标记跳过当前full核验。请求节省统计只计算实际省略的独立请求，不重复计算原增量已经跳过的楼。

来源拒绝、鉴权失败、限流继续按已有闸门处理，不从错误响应提取零计数。整体结果仍通过原缓存版本/所有权校验和原子交接发布；新任务失败保持旧状态可读。

## 验收标准

- 在相同固定来源、相同其余楼处理方式下，N个原本需要请求详情且全部符合条件的零楼，observe比verify少N次详情请求，根评论ID、UID、正文和数量完全一致；verify不省略。原增量已跳过的楼不能计入节省数。
- 正例：合法零、空/null/缺失预览、重复一致观察；反例：缺失或非整数计数、非零辅助计数、预览冲突、错误身份/来源、历史非零/不可用、同楼观察矛盾。
- 特别反例：主列表报告零后新增回复，结果必须保留“仅观察”语义，后续变为非零或到期verify时能获取，不宣称即时无遗漏。
- 首次observe成功后，下次未到期auto不会仅因partial重抓所有非零楼；已有但不可信基线不能误走首次例外。跨期限恢复仍可完成原observe任务，但期限不变，下一新建auto必须verify；间隔调整、重启和持续更新不能延后已有期限。
- 旧协议导入、坏/未知可选扩展不破坏核心读取；历史标志只单调收紧；复制旧完成证明不能冒充本轮完成。缺席旧零楼、同小时/活动任务full请求复用、取消、预算、恢复、数据库回滚、双状态摘要计数及前端说明均需测试。
- 与尾部增量联合测试：不同楼分别省略零详情、尾部更新或完整获取，证据不混用，旧评论不被删除。
- 真实来源仅做有限对照；性能以固定数据集请求数与分阶段耗时验收，不把样本一致或理论节省量当成普遍保证。
