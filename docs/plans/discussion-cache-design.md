# 视频讨论采集与小时缓存：需求设计

## 状态与授权范围

用户要求先审阅设计，再编写任务计划，最后实施。已确认北京时间自然小时刷新、PostgreSQL、部分结果可查看但不自动覆盖旧发布状态，以及不保留历史、仅展示最新状态。本文件只记录设计，不包含任务计划或业务实现。

## 已确认需求

- 输入指定 Bilibili 视频／番剧剧集链接，解析对应评论区。页面样式后续实现。
- 保存链接和采集结果，相同视频由所有访问用户共享缓存。
- 主评论及其楼中楼均需采集，每条发言对应 UID 和昵称，按根楼组织上下文。
- 只有首次无缓存或用户主动刷新才启动采集，不进行每小时定时更新。
- 使用 Asia/Shanghai 自然小时划分状态：16:59 发起的任务属于 16:00 小时，进入 17:00 且旧任务结束后可以再次刷新，无需等待满 60 分钟。
- 不能保证取得被删除、隐藏或接口不返回的内容，完整性必须可见。

## 当前归类范围（更新）

主评论及楼中楼按根楼组织，记录每条评论 UID、昵称和回复关系。用户新增了文件导出要求：从同一批数据生成按楼和按 UID 跨楼归类的评论文件，供其他脚本读取。详见 [评论导出协议设计](2026-09-05-comment-export-design.md)，该新增约定替代此前“本阶段不汇总跨楼发言”的边界。

楼名只保存来源实际提供的标题，缺失为 null，不虚构。用户画像、倾向分类、模型调用、单楼或视频级表现分析仍不在本阶段范围；文件归类不代表这些分析已实现。

## 设计方案

### 链接与共享身份

将原始链接映射到规范化视频标识，再映射到评论区标识。分享参数和不同入口不生成重复缓存。未知链接首次解析可能访问 Bilibili，已识别链接优先本地查找。仅允许合法 Bilibili 来源，短链每跳重新校验，禁止任意地址和内网请求。

### 时间、刷新与并发

小时由服务器按北京时间计算，存储时间采用 UTC。记录请求/任务创建时间、小时标签、实际采集开始和完成时间，禁止将小时标签当作源站精确瞬时快照。

每视频同一小时只创建一个逻辑刷新任务；每视频最多一个活动任务，跨整点仍不得并行重复抓取。小时归属取任务创建时刻，进入队列或恢复执行不改变其归属。失败重试复用同一任务并保留尝试记录，有限重试不能绕过限速；具体重试预算在实施前确定。

缓存过时不自动抓取。普通查看返回最近发布版本；只有主动刷新才检查新小时资格。前端禁用刷新按钮仅用于提示，后端须在事务中原子地检查小时资格和任务唯一性。建议使用视频标识与小时桶的唯一约束，以及活动任务锁/租约，避免多进程竞争。

刷新时当前发布状态继续可读，新数据写入临时工作状态。成功发布时在事务中切换当前状态指针，再清理不再引用的旧数据。页面请求携带状态 ID；旧状态已被替换时返回明确的状态过期响应，让页面重新加载，不能拼接新旧分页。首次采集无已发布状态时显示进度；中断不破坏当前状态，重启可恢复任务。

部分结果允许查看，必须标记“不完整”并显示缺失范围和失败原因。有已发布状态时，部分结果不自动覆盖它；页面默认展示已发布状态，并单独提供最近一次部分结果入口。首次采集受限且没有已发布状态时，展示带明确标记的部分结果。成功发布后删除此前的临时/部分结果；未成功时只保留最近一次部分工作状态供恢复或查看，不累积历次失败数据。

### 数据结构与版本

已确定使用 PostgreSQL 作为持久存储，第一版不引入 Redis。

| 对象 | 关键数据 |
| --- | --- |
| 视频及链接别名 | 规范化身份、标题、原始链接映射、当前发布版本 |
| 用户 | UID；昵称保留采集快照，不按昵称合并身份 |
| 楼 | 视频标识、根评论 ID、楼主 UID/昵称、主评论正文、来源提供的标题（若有）、最后核验时间 |
| 评论身份 | 评论 ID、根楼、父评论、发言 UID、可确认的目标 UID |
| 评论观测记录 | 正文、昵称快照、点赞等观测数据及观察时间；由当前或临时状态引用 |
| 讨论状态 | 小时桶、采集区间、范围、完整性；仅当前发布状态与最近一次临时工作状态 |
| 状态成员 | 状态 ID、评论 ID、引用的评论观测记录 |
| 采集任务 | 分页进度、租约、错误、尝试次数和状态 |

所有外部 ID 为字符串。采集时不能原地修改当前发布状态正在使用的观测记录，应临时保存变化记录；未变化记录可复用。记录每楼最后核验时间，不能把沿用旧楼自动称为本小时已验证。发布后回收失去引用的记录，不建立永久评论版本档案。

按视频/根楼、楼/发布时间查询建立索引。保留每条评论的发言 UID；跨楼文件归类已实现，数据库按 UID 查询和索引见 PostgreSQL 子阶段设计，页面和用户分析另行实施。返回页面时分页，楼中楼按需加载；采集范围不随页面分页缩小。整楼 JSON 可作为导出形式，不作为每次覆盖整个视频的主要存储方式。

不保留历史小时快照，不提供历史选择、回看或对比接口。只持久保存当前发布状态；为刷新失败保护而保留的旧状态是刷新期间的当前状态，不是历史档案。最近一次临时工作状态属于恢复/部分查看用途，不作为第二个历史版本。发布后的回收应可幂等重试，防止故障导致旧正文长期累积。任务可保留必要的时间、状态和错误元数据，但不得借任务日志留存历史评论正文。

### 采集协议与待验证约束

主评论适配器使用网页的 `/x/v2/reply/wbi/main`，第一版优先时间排序 `mode=2`：计算标准 WBI 请求签名，使用 `pagination_str` 传入返回的 `next_offset`，检查 `cursor.is_end` 并检测重复游标。热门排序 `mode=3` 仅用于必要的覆盖交叉核验；热门排序结束不能作为全部可见主楼已取得的依据。楼中楼使用 `/x/v2/reply/reply`，请求 `ps=20` 并校验响应页码、容量和报告数量；服务端可能限制容量，不能依靠增大 `ps` 假定减少请求。顶置评论须与普通主评论按 ID 去重归类。不能硬编码永久签名参数或通过猜测页码代替实际游标。

采集客户端采用 Python httpx，显式设置如 `BiliBiliTalkView/0.1` 的应用 User-Agent，不依赖默认库标识，不伪装登录状态。主评论使用网页 WBI 协议；公共签名参数需按来源更新，不作为账号凭据。若遇到 HTTP 412 或业务拒绝（包括 `-352`），停止本次采集并将运行与当前楼标为受限，保留当页之前的事务断点；不能将拒绝当空楼、继续遍历其他楼或自动重试。错误码本身不能证明具体原因，也不能据此认定登录即可恢复；须先核验正常页面访问和可用授权方式，再决定恢复条件。生产阶段需将 httpx 纳入运行依赖并更新锁文件。

主楼跨页重叠与游标循环分开判定；单页没有新 ID 或不足一页不能证明源站已结束或拒绝访问。当前候选保护为连续 5 页没有新 ID 时停止并标未完成，出现新 ID 后重置计数；异常空页、重复游标及接口拒绝立即停止。切换排序必须新建游标上下文。每页记录、连续重叠计数与下一游标原子提交，中断恢复只从最近提交点继续，不通过恢复清零保护预算。

主楼末页和全部楼内回复分别验收；单个样例主楼遍历通过不能推广为所有视频或服务器环境均可用。所有楼回复及目标服务器访问仍需验收。页面/接口总数、实际去重主楼数和实际回复数分开记录；主楼的 `rcount` 仅作为报告数量，不替代逐楼分页读取。即使主楼与报告回复之和接近总数，也不能宣称评论全量已采集。只通过正常授权处理登录和权限限制。新评论以评论 ID 集合差异识别，已有记录逐字段比较；旧记录未再观察到不自动等于删除，未完成覆盖核验不能宣称无新增。

### 增量更新的边界

先验证主楼与楼中楼分页，再设计采集优化。数据库按评论 ID 去重和记录变化，不等于接口可只请求变化的楼。老楼也可能新增回复，数量相同不能证明内容不变。页面未返回评论不能直接判定删除。

第一版优先保证覆盖证据，允许请求后差异入库；后续根据实测变化信号减少请求，并对未核验楼明确标识。正文/回复关系变化生成新上下文版本，为未来按楼重新分析准备；点赞变化是否影响模型缓存留待模型阶段。

### 组件与接口边界

建议划分链接解析器、Bilibili 适配器、持久任务执行器、上下文组装器和快照查询服务。长采集任务不依赖浏览器连接或单个 HTTP 请求存活。模型客户端和模型 API 调用不属于本次功能。

接口语义建议：提交链接返回缓存或任务；查看视频返回当前快照与下次刷新时间；刷新返回新建/复用任务；查询任务返回进度和限制；分页读取指定快照的楼和回复。具体路径、状态码和数据库迁移在各子阶段计划中确定。

## 设计验收要点

- 相同视频的不同链接复用数据；多人同时刷新只产生一个任务。
- 16:59 → 17:00、跨日、排队跨整点和任务跨整点的归属正确。
- 新小时普通查看不触发采集，手动刷新才更新。
- 失败不覆盖旧数据，中断恢复不重复，重复页和空页不误判完整。
- 同一状态分页和楼内查询一致；状态过期明确要求重新加载，每条评论的身份与回复关系可追溯。
- 新回复只改变对应楼的上下文；新状态成功发布后旧状态及无引用内容被清理，无历史回看。
- 部分结果明确标记且不自动替换已有发布状态；多次失败不累积历史正文。
- 缓存重启仍存在，公开输入有 URL 校验、请求限额与全局并发限制。

## 登录态与动态回复的实现约束

服务器采集由独立 Python 进程执行。登录态仅从后端受保护的配置或凭据文件读取，不依赖 Agent、桌面浏览器或聊天传递，不写入日志/Git；仅对固定来源域名使用，禁止携带凭据跟随任意重定向。登录态单次成功不等于持续可用，遇到新的拒绝仍停止并等待核验。

采集期间楼内报告数量增长可在预算内继续读取，但该楼必须进入待复核状态；独立重读同楼，比较 ID 集合、正文及非文本内容、UID、昵称、父关系和尾页证据后才允许提升完整性。再次发生计数变化或覆盖不一致则保留未核验状态，不无限循环。字段变化保留最新观测并分开记录差异，ID 相同不能解释为全部字段未变；展示附属元数据与分析上下文字段的失效规则在后续模型阶段确定。

取得全部返回回复不等于所有父节点均可得。父评论 ID 不在同楼结果或主评论中时，保存缺失引用及其来源，禁止将缺失父节点自动判为删除或改接到楼主；分页核验状态与上下文缺口状态分开记录，后续展示和模型上下文须明确该缺口。
