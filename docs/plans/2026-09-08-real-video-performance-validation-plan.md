# 真实视频性能验收计划

## 目标与已确认范围

用户已确认对 ep4292435 和 ep1231536 执行端到端性能验收。分支为 `opt/real-video-performance-validation`，基线 main 为 5cbbe4a。本轮不新增采集策略、页面或AI功能。

## 设计与测量口径

使用现有服务器 Python 采集器及共享来源访问控制，在独立忽略目录保存工作集和计时证据。保留2秒来源间隔、真实时钟、原预算与冷却，不修改历史数据来制造首次采集或新增场景，不覆盖 D:/Data。首次采集使用新的测试工作集；刷新以该工作集或已验证基线副本为起点。数据库验证使用独立测试schema，不覆盖现有网页结果。

测量总时长、请求数量、请求/限速等待、检查点提交、数据集准备及SQL物化。嵌套阶段不重复相加。保存采集起止时间、版本、实际策略、去重数量和coverage；大视频若受限或预算停止，明确属于部分测量。

无新增/有新增由评论ID集合差分及楼归属核对确定，不单凭总数。来源删除/隐藏、旧缺口补齐与真正新评论分开标记。真实场景未出现时列为未观测，不伪造评论或变更时钟。通过同一已记录输入的离线重放补充旧/新处理成本比较，不能把不同时刻的来源请求直接当作严格A/B。

## 异常与交付边界

当前凭据失效、来源拒绝或网络不可达时，保留断点，不通过新控制目录规避限制。只做必要的有限诊断；需要新的登录会话时说明待用户操作。临时报告、原始响应、个人数据及性能脚本留在 `data/verification/`，Git仅保存本计划及确有必要的开发变更。验收完成后按既定 squash/main/push 约定保存。

当前执行约束：两个指定视频的首屏接口报告数量接近，因此按实测规模标注，不预设大小类别。计时包装仅用于本轮独立测试schema中的生产worker；请求含共享间隔和请求钩子，间隔时间作为其中子项，不能与父项相加。来源闸门同时检查开发部署状态和测试worker状态。

初始采集与工作集/数据库语义核对已完成。刷新使用独立初始备份进行ID及发布时间差分；现有服务内部资格字段为can_refresh，临时工具沿用该字段。两视频的partial均需结合零回复观察策略解读，不能以来源计数相等覆盖该语义。首次运行还包含链接解析，执行耗时采用perf_counter及worker阶段边界；captured_from/to是数据观察窗口，刷新可沿用基线起点，不能用来计算刷新运行时长。首次会话包含额外链接解析，统计时明确会话边界。


## 验收收口与后续设计输入

两视频的首次采集及各一次真实刷新已完成；分别观测到有新增和无新增的刷新场景，并非每个视频都观测到两类刷新。评论去重、旧记录保留、UID/楼关系、正文和数据库语义核对通过；固定真实输入的旧新准备链路摘要一致。来源访问没有阻断，partial继续表达零回复观察及复用未经本轮逐条核验的覆盖边界。没有修改业务代码，实测材料及初始基线留在忽略目录，原网页缓存不被替换。

下一阶段候选：优先研究零回复状态的逐楼持久化，减少重复处理整份metadata，仍保持断点、安全预算与证据原子性。其次研究主列表/详情正文视图差异导致的重复核验：本轮存在主列表正文未变、却与已核验详情正文签名不同的楼；不能简单取消复查，应在新设计中约定各视图签名及反例。上述仅为后续设计输入，本分支不实施优化。
