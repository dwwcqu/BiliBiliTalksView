# 评论增量刷新与正文复用：设计

## 状态与目标

用户已确认刷新应优先复用已保存评论，只补新增及确实变化的记录。本文件细化网络读取、数据库写入和文件导出三个不同层面的增量；正文存储复用单元已实现并通过隔离数据库迁移验收；现有开发数据库尚未升级；选择性采集已由独立refresh CLI实现，本地队列/worker已实现，HTTP接入仍未实现。

依据：[后台任务设计](2026-09-06-background-cache-design.md)、[存储基线设计](2026-09-06-postgresql-storage-design.md)、[协议2.0.0](../references/comment-export-protocol-v2.md)。小时资格、全局限速、受限恢复和英文目录规则不变。

目标是减少来源请求和大段正文重复写入，不承诺零读取旧数据。数据库仍需查ID/摘要，来源主楼接口也可能顺带返回已存正文；不能将“按ID去重”称为只请求了新增评论。

## 两种刷新模式

| 模式 | 行为 | 完整性 |
| --- | --- | --- |
| incremental | 扫描主楼列表，以变化信号选择需要重读的楼；其余复用基线 | 未重新核验的范围显式标记，通常为partial |
| full | 重新核对整个主楼清单及各楼回复，并检查基线中未再次出现的楼 | 按实际覆盖标记；资源不可用时仍可能partial |

公共刷新请求可选mode=auto/full，auto由服务端选择；不提供绕过完整核对周期的强制incremental参数。请求的auto/full意图和原小时在任务创建时固定；worker首次领取时选择有效模式、冻结最新可用基线并持久化，避免排队跨越24小时后仍使用过期决策。开始采集后恢复执行不改模式或基线。同小时已有任务时返回它，不另建一次全量请求绕过配额。

没有可用基线、上一次全范围尝试未完成，或距离last_full_scan_completed_at超过24小时时，下一次用户主动刷新选择full；否则选择incremental。24小时是可配置的本项目策略。不会因到点、普通访问或无用户请求而自动新建采集任务。

last_full_scan_completed_at只表示本轮所有计划目标均已核验或取得明确不可用终态，不等于coverage=verified。这样有不可用楼的视频不会因永远达不到verified而每次都被强制全抓。未完成的全范围尝试不更新此时间。预算不足时保留partial并报告未核验范围，不自动提高预算或无限重跑全量。

## 基线与任务一致性

任务选择最新已成功物化的可读状态作为基线（current或partial working），不选loading/failed/未发布ready。保存base_state_id、基线摘要及refresh_mode，先冻结基线再访问来源。partial基线中真正未完成采集的范围必须补核；因主动复用而标partial的范围不因此强制重抓。选楼依据内部核验证据，不直接使用导出的partial标记。

冻结在一致数据库读快照内完成：将完整基线记录、正文和逐楼核验证据复制到任务已有的持久工作集，原子标记冻结完成后才允许来源请求。冻结不完整时可在尚未发出请求的前提下重新选择基线。恢复不依赖原状态或payload仍存在；base_state_id只作来源标识，不设阻止旧状态回收的外键。

同一视频只允许一个活动job。冻结时同时保存视频缓存版本号（所有改变可读状态的导入/发布均在事务中递增），提交前在视频行锁内比较版本并校验任务所有权。若管理员导入已改变基线，以baseline_changed结束本任务，不覆盖更晚的数据，不自动另建任务或重置预算。其他可恢复失败保留原工作集与预算；任务结束后的工作集按现有清理规则回收，不形成长期历史。

新状态由“基线记录＋本次实际返回的新记录/变化”合成，不只存一个增量列表给网页。评论ID是身份键，时间用于排序，不能用最大的评论ID推断后面一定没有新评论。

## 网络读取策略

### 主楼

首版incremental仍使用时间排序完整遍历主楼列表，检查游标至有效结束。这样能看到旧楼的最新回复数量，而不是只看评论区头部。遇到一个旧ID、短页、总数相等或连续旧ID不能作为提前结束依据。

主楼API目前返回正文与元数据，因此旧楼主正文可能随响应再次传回；真正减少的是不必为每个未变化旧楼再次遍历楼中楼。不虚构来源存在“只返回新增评论”的接口。

每个主楼按ID对照基线，记录是否新增、根正文/媒体是否变化、报告回复数是否变化、是否曾不可用或未核验。本次看到的根评论使用实际观测时间；未看到的基线根评论不能改成新的collected_at。

### 楼中楼

| 条件 | incremental处理 |
| --- | --- |
| 新楼 | 完整读取该楼回复，包括零回复核验 |
| 内部reply_check_state=needs_check | 重新读取/完成该楼；包括真实分页中断、异常、无可靠基线证据 |
| 报告回复数增减，或根正文/媒体变化 | 重读该楼全部回复，再按ID比较 |
| 已不可用的楼重新出现在主列表 | 优先重新核验，成功才解除该楼标记 |
| 有最近一次完成的回复核验依据，报告数和根上下文无变化 | 复用回复；标记本轮未重新核验，不宣称无变化 |
| 原已不可用且本轮主列表仍未出现 | 保留既有内容/不可用信息，等full或管理员定向复核，不反复请求同一不可用根 |

选楼保留reply_check_state=complete/needs_check/source_unavailable，与本轮checked_now/reused_unverified分开。complete表示最近一次源端遍历已完成，保存该次核验时间、报告回复数和根正文/媒体摘要；连续复用不更新这组比较依据，也不将complete改成needs_check。真实采集未完成、失败或缺乏可靠核验证据时进入needs_check；未出现在本轮主列表、无法比较的旧楼保留未观测标记并等待full，已知needs_check仍需补核。

首版不从ceil(count/page_size)倒推尾页来承诺只读新增回复：删除或插入会移动页边界，且仅尾页不能覆盖中间变化。变化楼先全楼核对，避免无证据的分页优化。未来若验证了可靠变化游标/版本标识，再替换该策略。

数量不变可能是新增和删除抵消，也可能只有内容/昵称/点赞变化。因此“信号无变化”只决定快刷是否省略请求，不是完整性证据。HTTP拒绝、身份冲突和异常分页仍沿用现有停止/恢复规则。

## 新增、变化与未观察到

- 新comment_id：新增一条记录。
- 同ID的正文、图片/表情或未知正文扩展变化：创建新内容载荷，并让新状态引用它。
- 仅点赞、昵称或其他已定义观测小字段变化：只更新新状态的相应小字段，不复制正文。
- UID或root_id与已知身份冲突：保持原数据并进入核对，不按普通更新覆盖到另一个用户/楼。
- 本次未返回的旧评论：本版不自动删除，保留最后实际观测值并标明未重新观察；不能仅凭缺失推断永久删除。
- 来源明确不提供该楼：保持不可用终态和已有评论，不生成空回复来填补缺口。

工作集分别保存本轮实际观察ID集合与最终保留成员集合，不能用合成后的数量冒充本轮采集数量。即使分页已正常到尾，只要输出仍含本轮未观察的继承回复，该楼仍标partial/replies_incomplete，继承回复保留旧collected_at；继承且未观察到的根评论使主楼覆盖标partial/main_incomplete。源端遍历完成证据独立保存，因此full已处理全部计划目标时仍可更新last_full_scan_completed_at，不因保留旧内容永远重复全抓。

full也不静默删除基线内容；当前保留的是每条评论最后已取得的观测，不建立多个历史正文版本。若后续希望清理已不再可见的评论，需单独确认删除政策，不能借增量优化改变用户数据保留要求。

## PostgreSQL写入复用

原0001存储在每个状态复制完整正文。现已增加0002_comment_payloads迁移及引用读写；升级后复用正文，尚未升级的数据库仍保留原结构。0003_cache_handoff已增加基线版本与状态内部上下文，数据交接接口详见[后台交接计划](2026-09-06-background-handoff-plan.md)。后台任务字段与worker调用已由C2调度模块接入。

| 对象 | 新职责 |
| --- | --- |
| comment_payloads | payload_id、video_id、comment_id、content_hash、content JSONB、extra_fields JSONB；(video_id,comment_id,content_hash)唯一 |
| comments | 保持(state_id,comment_id)成员主键，新增payload_id引用；保留root/parent、kind、UID、昵称、时间、点赞等小字段 |
| threads/状态观测信息 | reply_check_state、最后完成核验的时间及比较依据、本轮观察ID/继承范围、当前处理方式；不把旧验证时间改成现在 |
| collection_jobs/视频缓存版本 | base_state_id、冻结工作集摘要、预期缓存版本、refresh_mode、last_full_scan_completed_at依据、差异统计 |

载荷摘要基于解码后的content与未映射正文扩展，使用确定性JSON序列化；排除schema_version、export_id、collected_at、点赞和昵称等不属于正文载荷的字段。数组顺序有意义，字段排序或缩进无意义。JSONB会改变整数型浮点数的表现形式；摘要前递归将整数型float按Decimal(str(value))转int（包括负零），使1e20与等值整数、-0.0与0共享摘要，避免数值表示变化造成伪冲突。迁移和运行时代码使用相同版本的规则。数据库仍使用已约定的可逆字符编码。

摘要与逻辑内容相同则引用已有payload，不重新INSERT大段正文。comments作为状态成员仍需写轻量引用和观测字段；这不是零数据库写入，也不是消除所有磁盘复制。根楼与用户查询通过成员表联接载荷，对外还原同样的评论对象。

payload引用须同时约束video_id、comment_id，防止把另一条评论的正文挂错。新状态原子提交，旧状态的引用在发布/替换后回收；只有不再被任何保留状态引用的旧payload才可删除。活动任务使用已冻结的完整工作集，不依赖这些数据库引用，回收无需等待任务完成。保留current和最近working，不增加历史状态列表。

迁移须逐条验证ID、正文、关系和计数无损，先回填payload及引用，再切换查询/写入，不能DROP用户数据库重建。现有v1/v2文件导入仍受支持，同ID去重与payload复用属于内部存储实现，不改变外部身份字段。

## 覆盖与显示

内部逐楼记录本轮处理方式reply_verification=checked_now/reused_unverified/source_unavailable/not_checked；checked_now只表示本轮已执行检查，完整与否由独立reply_check_state和分页证据确定。保存last_reply_checked_at及最近一次完成核验的时间/比较依据。实际读取到的评论更新collected_at，继承记录保留旧时间，绝不把整个基线伪装成刚抓到的数据。

文件协议2.0.0不增加新字段或原因码：未重新核验的楼回复分页标partial，使用已有replies_incomplete；主列表确实到尾且输出未混入本轮未观察的旧根，才标主楼分页verified。源端遍历已完成与输出覆盖完整是两个独立事实。整体包含继承未核验范围时为partial。HTTP接口可额外展示刷新模式、继承未核验数量、本轮检查时间和最近全范围尝试时间。

当前先沿用“current完整状态优先，最新partial单独入口”的已确认发布规则；快速增量不因抓取动作结束就自动覆盖旧完整current。若页面改为默认展示最新增量状态，必须同时突出partial/未全量核验，且不把显示选择等同于将数据库coverage改为verified。本稿暂沿用旧规则；只有用户明确选择新的默认展示方式后才修改，不能因增量设计自动改变发布政策。

没有发现新ID只能汇报“本次未发现新增”，不能汇报“所有评论均无变化”。统计分别包括new_comments、changed_payloads、metadata_updates、reused_payloads、reused_unverified_comments和source_requests，不能把未请求的旧评论算作已核对未变。

## 文件导出与现有流水线

下游继续接收完整的协议2.0.0批次，包括旧评论和新增评论两种分类；不要求其他Agent自行合并增量碎片。每次导出生成新export_id，所以即使正文被数据库复用，也仍需生成带新批次标识的完整JSONL文件，不能原地追加旧current或直接复用带旧export_id的文件。

这意味着网络/数据库增量不等于文件导出零重写。首版worker可以继续复用现有冻结、校验和原子导入流程，但导入端选择已存payload，避免重复写正文；按需导出与直接增量入库的进一步提速留到有实际性能证据后再实施。

内部证据不能仅靠v1/v2文件恢复。采集检查点必须持久化逐楼核验状态、比较依据、本轮观察集合、继承范围及full完成证据；worker将其作为专用导入上下文，与冻结批次的video_id、任务ID、基线版本及批次摘要绑定校验。新状态、内部证据和任务结果在后台任务设计约定的物化事务中一并提交；证据缺失/不匹配不得发布成功或静默降级，保留旧缓存并报告错误。

普通CLI文件导入仍可使用既有协议，不要求提供worker上下文。对合法verified楼仅初始化该文件证明的核验依据；partial楼无额外可信证据时设needs_check，不能根据文件自行推断不可用终态、主动复用或已完成一次full。无可信full完成时间的基线，下一次auto采用full。内部上下文不作为新增协议文件交给下游。

## 验收与阶段安排

必须覆盖：新增根、新增旧楼回复、相同计数但ID替换、点赞/昵称变化不产生新正文载荷、正文变化产生新载荷、旧楼未返回不删除、partial基线补核、资源恢复、无变化时不重复INSERT正文、刷新中断、旧状态持续可读、基线改变拒绝覆盖，以及再次导出与完整状态查询一致。

追加回归场景：连续两次快刷均跳过无变化且有完整核验基线的回复；源端从10条变9条而保留10条时仍partial；缺失旧根不冒充本轮主楼verified；重启后内部证据可恢复；普通partial文件导入保守补核；管理员回收原状态/payload后冻结任务仍可恢复、但提交因版本变化拒绝；worker上下文错配或事务失败不产生可见半成品。

常规测试使用虚构响应和独立PostgreSQL，不为“验证增量”自动重抓真实视频。实现时明确对照全抓的请求数和正文写入数，但不能拿单个样例的节省比例承诺所有视频。

本设计已完成审阅。分阶段执行顺序及首个存储复用单元详见[增量刷新实施计划](2026-09-06-incremental-refresh-plan.md)。数据库CLI已接入正文载荷复用；独立refresh CLI已实现工作集/协议文件基线与选择性采集，见[采集核心计划](2026-09-06-incremental-collection-plan.md)。collect仍保持原全量行为；后台物化已接入本地worker；HTTP及界面尚未接入。
