# 分阶段交付与需求确认流程

## 工作规则

每次只实施用户确认的一个阶段或阶段内子任务。下表是建议顺序，**不是对全部功能的一次性实施授权**。用户调整优先级后先更新范围，不因已有代码或工具而自行推进下一阶段。

开始功能和优化任务时，依次执行：

1. 阅读 AGENTS.md、产品需求、现有代码和相关历史决策，确认已实现状态。
2. 列明目标、输入/输出、使用者、范围外事项、异常场景、验收标准和未决问题；聚焦询问真正阻塞设计的问题。
3. 用户确认具体要求后，给出设计与取舍：数据结构、模块边界、接口、扩展点、失败处理和安全影响。
4. 将确认内容与可执行计划存入 `docs/plans/YYYY-MM-DD-<topic>.md`；设计与需求合并在同一文件亦可。沿用会话中已确认的决定，不重复询问。
5. 实施当前范围，运行适当验证，更新文档并报告结果、限制与剩余问题。
6. 当前阶段交付验收后，由用户决定下一阶段；不把“规划中的能力”标成完成。

紧急缺陷也需先说明复现、预期行为和修复范围，流程可简化但不能跳过理解问题。新增需求影响已确认接口、标签定义或保存策略时，先记录影响再调整计划。

## 建议路线与验收门槛

| 阶段 | 交付范围 | 进入下一阶段前的证据 |
| --- | --- | --- |
| 0：环境基础 | 本地开发、生产构建、健康接口、Git、CI 与容器配置 | 当前已有骨架；此前本地构建和测试通过，容器实际构建与服务器部署仍未验证 |
| 1：采集可行性 | 明确视频链接范围，验证身份信息、主楼/楼中楼分页与限制 | 少量真实样例包含 UID、昵称、评论和回复关系；解释空页/受限情况，报告覆盖边界 |
| 2：采集与存储 | 数据模型、迁移、任务状态、限速、去重和断点续采 | 中断恢复不重复，失败可追溯，身份和上下文正确，数据可持久化 |
| 3：讨论浏览 | 提交链接、进度、视频概览、楼内对话、用户发言定位 | 能从用户与模型证据定位原评论；缺失和部分完成状态清晰，无伪造数据 |
| 4：分析规则与验证 | 确定维度、标签定义、模型 API 契约、评估样例和预算 | 用户认可规则与样例评判；明确误判处理和证据标准 |
| 5：分析接入 | 后端模型请求、结果校验、上下文版本、证据展示 | 超时、限流、无效输出、超长楼和预算上限均可处理；判断可复核 |
| 6：服务器上线 | 公网访问控制、HTTPS、持久化、备份、监控及部署 | 容器与目标服务器实测、备份恢复和回滚验证；确认服务器采集可用性 |

部署能力应在各阶段持续保持，但正式上线独立验收。数据库、队列和模型供应商在相关阶段按需求确定，不因路线提到就立即安装或开发。

## 单个任务计划模板

```markdown
# <功能名称>
## 当前阶段与目标
## 已确认需求及会话依据
## 待确认问题
## 本次范围与范围外事项
## 设计与取舍
## 数据/API 契约及兼容性
## 实施步骤与涉及文件
## 验收样例、失败场景与验证命令
## 数据安全、成本及部署影响
## 实际结果与后续事项
```

计划进入实施前，不得仍有影响实施的未决项；确实后置的问题应明确所属阶段。复杂功能可以拆子任务，但不扩展到下一个阶段。

## 变更和验证约定

- 文档变更检查链接、事实和命令即可；不为纯文档修改启动业务服务或付费调用。
- 后端修改运行相关 pytest 与 Ruff，前端修改至少运行生产构建；为新增交互按需要引入行为测试。
- 采集测试覆盖去重、重复页、空页、无权限、缺失用户/父评论、超长 ID 和中断恢复。
- 分析测试使用假模型响应或脱敏固定样例；真实调用需属于当前确认范围，记录实际成本与覆盖。
- 报告“已通过”须有本次验证证据；无法验证时注明原因，不将配置检查等同于容器运行成功。
- 变更依赖同步锁文件；数据库变更带迁移，API 或分析结构变化记录版本兼容策略。
- 提交/PR 描述当前问题、最终行为、验证结果和已知限制；大范围设计调整记录原因。

## 分支与远端保存

主分支固定为 `main`，远端固定为 `git@github.com:dwwcqu/BiliBiliTalksView.git`。开始每个独立功能前获取远端更新，从同步后的 `main` 创建 `feat/<topic>` 分支。该功能的需求、设计、计划、实现和测试均在同一个 `feat/` 分支完成，不为功能规划文档另建 `docs/` 分支；仅独立于功能的维护任务可使用 `fix/`、`docs/`。开始工作前明确告知分支名称。本次首次仓库初始化可直接提交到 `main`。

“完成所有功能后合并”指完成当前功能分支内已确认的全部工作，不是一次做完整个网站。功能验收和相关检查通过后合并回 `main`，合并成功必须自动执行 `git push origin main`。用户已持续授权该保存步骤，无需每次重新确认。获取远端后比较本地 HEAD 与 `origin/main`，才可报告远端保存成功。

推送失败时保留本地提交，说明认证、网络或保护规则等具体原因；禁止强制推送、覆盖远端历史或绕过分支保护。远端要求 PR 时按保护流程操作。

## 文档入库边界

仓库仅保存需求、开发设计、任务计划、代码、测试及必要工程配置和使用说明。排查报告、实测报告、执行日志、接口响应和第三方脚本不入库；结果在对话中汇报，临时证据仅存于已忽略的本地目录。将影响实现的协议决策和未解决约束提炼到设计或计划，不复制完整排查过程。
