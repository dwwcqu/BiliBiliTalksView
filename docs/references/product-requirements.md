# 产品需求与数据约定

## 目标与当前边界

建设可在 Linux 服务器部署、通过链接访问的 Bilibili 讨论分析网站。主流程：指定内容 → 采集评论及楼中楼 → 还原用户与对话 → 按楼通过模型 API 分析 → 展示证据与结果。

本文件区分已确认需求与待定设计，不表示功能已实现。当前已有基础采集页面、HTTP API、独立评论采集/导出 CLI、PostgreSQL 存储和持久队列/worker，以及 Docker 配置和 CI。当前页面仅输入视频地址、查看采集进度和保存摘要；讨论浏览与 AI 页面后续另行设计。隔离数据库测试及前端模拟交互已验证，现有开发库已在备份和恢复演练后升级，真实页面缓存与任务提交已验证；真实采集最终入库与页面结果已核验，源端不可得内容明确保留 partial；目标服务器运行仍须单独验收。

“IP”暂指作品／系列，**不是网络 IP 地址**。已有明确输入为指定视频链接，番剧剧集亦属讨论范围。作品如何建档、是否自动发现整部作品的视频、是否包括相关二创、动态或专栏评论，须在对应阶段确认；不得自动扩大抓取范围。

## 已确认的核心需求

1. 尽可能详细地获取授权访问范围内的可见评论，包括主评论和全部可取得的楼中楼。
2. 每条评论必须对应发言用户 UID 与昵称，主楼及其全部回复组成一个分析上下文。
3. 保留回复关系，以支持时间顺序阅读、对话树和用户发言定位。
4. 后端通过 API 调用大模型，分析整楼氛围及参与用户在该楼中的讨论倾向。
5. 情绪发泄、合理讨论、挑拨对立是候选维度，具体定义、是否多标签、评分及展示方式尚待确定。
6. 分阶段实施，需求与验收标准确认后再设计、计划和实现；允许后续优化和添加功能。

## 用户、评论和上下文约定

以下是后续设计必须保留的信息，字段名可在数据库/API 设计时调整：

| 对象 | 必须表达的信息 |
| --- | --- |
| 内容来源 | 原始链接、规范化链接、视频/剧集标识；作品归属另行确认 |
| 用户 | UID、采集时昵称；UID 为关联键，不使用昵称去重 |
| 评论 | 评论 ID、内容来源、根楼 ID、父评论 ID、发言 UID、正文、发布时间、点赞数、采集时间 |
| 回复对象 | 可确认的目标评论 ID、目标 UID，以及关系来源或未知状态 |
| 采集记录 | 抓取范围、排序方式、分页进度、去重后数量、接口报告数量、错误及完整性状态 |
| 分析记录 | 上下文版本、楼 ID、模型与提示词版本、结构化结果、证据评论 ID、执行状态 |

- 所有外部标识以字符串传输和存储映射，避免 JavaScript 大整数精度丢失。
- 区分根楼关系、直接父评论关系和正文中的 @ 提及；不能将提及自动推断为直接回复。
- 昵称相同不合并用户，昵称变化不创建新 UID。UID 缺失时保留评论并明确身份不可确认，不伪造关联。
- 单集统计与整部作品统计分开保存并明确展示口径。
- 时间存储采用统一时区或带时区时间，展示时转换；保留接口原始时间便于追溯。
- 原始正文与清洗后的模型输入分开处理；图片、表情、删除节点等非文本或缺失内容必须标记。

## 完整性与采集可靠性

“全部”指采集时当前权限下可以取得的全部可见内容，不涵盖删除、隐藏或无权访问内容。历史探查仅验证了一个剧集的统计、首屏评论和一页楼中楼；主评论第二页曾返回成功状态但空数据，不能据此认定分页可用或采集完整。

采集器设计需覆盖：分页终止依据、重复页检测、限速、有限重试与退避、断点续采、幂等去重、取消、超时和失败原因。区分待采集、进行中、已完成、部分完成、受限和失败；具体状态机在采集阶段确定。数量相等只是核对信号，不是完整性证明。

上下文绑定一次明确的采集快照，记录缺失父节点和未取完回复。采集期间新增或删除的评论不应被悄悄混入已经分析的上下文。网页展示采集时间、覆盖范围和限制；样本分析不得宣称代表整个评论区。

## 模型分析设计约束

- 每楼为基本分析单位，包含主评论、回复关系、发言 UID/昵称对应表和必要背景。发送字段、模型供应商和预算在接入阶段确认。
- 用户结论限定为“该 UID 在该楼、该上下文中的发言表现”，不推断永久人格、真实身份或主观恶意。
- 正常负面评价、意见不同与引战区分处理；允许多种倾向并存、证据不足和无法判断。
- 每项判断应能追溯到实际评论 ID 和证据片段。未知 ID、无效结构、臆造证据不得作为成功结果展示。
- 评论是待分析数据，不是指令。隔离评论中的提示注入，不让其修改系统规则、调用工具或读取密钥。
- 超长楼不得静默截断。设计分块时保留发言和回复标识，并记录覆盖范围、摘要步骤与可能损失。
- 保存模型标识、提示词/标签规则版本、上下文版本和成本信息；超时、重试、预算限制及重跑策略须明确。
- 在自动批量运行前，用人工审阅的脱敏样例验证误判、反讽、引用、争议观点和缺失上下文；模型结果是可复核分析，不是事实裁决。

## 安全、部署与扩展

用户提交 URL 时，限定允许的 Bilibili 域名与协议，并验证短链的每次重定向；禁止后端访问本机、内网或任意地址，避免 SSRF。评论按不可信文本渲染，防止 XSS。

Cookie、API Key 仅在后端配置，不进入浏览器、Git、模型上下文或普通日志。公开评论仍包含用户数据；设计保存期限、访问范围、删除和导出规则。公开网站是否公开分析对象的 UID/昵称，以及模型数据传输范围，须单独明确。

按具体需要拆分来源适配器、采集调度、上下文组装、持久化、模型客户端和展示层。通过稳定数据契约、版本化迁移和可替换客户端支持扩展；不提前实现多个供应商或复杂微服务。

公网开放采集或模型调用前，必须设计访问控制、请求限额、并发/费用上限；长任务移出 HTTP 请求生命周期。部署阶段验证数据库持久化、备份恢复、日志脱敏、HTTPS、健康检查和回滚。服务器上的 Bilibili 可访问性必须重新实测。

## 已确认的小时刷新规则

输入页及共享缓存的设计见 [视频讨论缓存设计](../plans/discussion-cache-design.md)。按北京时间自然小时分桶：16:59 发起的任务属于 16:00 版本，进入 17:00 且旧任务结束后可手动刷新，无需等待满 60 分钟。普通访问始终复用已有缓存，不因跨小时自动采集。小时标签与实际采集区间分开记录。

## 已确认的存储与保留策略

采用 PostgreSQL。每个视频只展示当前发布状态，不保留历史小时数据，不提供历史回看。刷新期间当前状态仍可用，新结果临时写入；成功发布后清理旧状态及无引用的评论观测记录。

部分结果可查看但必须标记不完整，不自动覆盖已有发布状态；没有发布状态时可展示部分结果。最多保留最近一次临时工作状态供恢复/查看，成功发布或后续任务替换时清理，不累积历次失败正文。小时标签、状态 ID 和上下文标识服务于一致性及后续分析失效判断，不代表需要永久保存历史上下文。

## 当前采集、文件归类与后续分析的界限

当前获取视频下主评论及楼中楼，保留 UID、昵称、根楼和回复关系。根据新增需求，同一批评论导出为按楼的完整对话和按 UID 的视频内全部发言两种分类；评论不从原楼搬走，两种文件保留一致记录。跨楼归类不包含用户表现评判、统计页面或模型逻辑。楼名仅在来源提供时保存。

当前新输出格式固定为 [评论导出协议 2.0.0](comment-export-protocol-v2.md)，该文件是当前数据契约依据；保留 [1.0.0](comment-export-protocol-v1.md) 读取兼容。生成目录使用 `threads/000/`、`users/uid_<UID>/` 和 `users/unknown/`，不含昵称、中文或空白；昵称与评论原文完整保留在 JSON 字段。后续按协议制定计划和实现；本阶段调试目标改为 ep4292435，README 暂为空，不生成视频简介。

## 增量刷新方向

刷新优先复用已保存正文，按评论ID识别新增与变化，避免把未变大段正文重复入库。来源请求仍需必要的旧楼检查，数量相同不证明内容未变。具体模式、payload复用和覆盖限制见 [增量刷新设计](../plans/2026-09-06-incremental-refresh-design.md)，正文载荷复用代码与迁移已完成隔离验收，开发数据库尚未升级；独立refresh CLI已支持基线、选择性采集和同任务恢复，本地持久队列/worker已支持共享小时刷新，HTTP任务与讨论接口已完成，基础页面尚未接入。
